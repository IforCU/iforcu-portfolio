> **프로젝트명**: Project A601 — "서기 2324년, AI 판사 기반 몰입형 SF 서바이벌 마피아 게임"

## 1. 프로젝트 개요

실시간 멀티플레이어 마피아 게임 웹 서비스를 설계·구현했습니다.  
플레이어들은 WebSocket으로 연결된 게임 엔진에서 페이즈(낮/밤/변론/판결)를 진행하고, LiveKit 기반 WebRTC로 실시간 음성 통화를 합니다. 변론이 끝나면 각 플레이어의 발언이 AI 서버로 전달되어 GPT 기반 AI 판사가 "처형 대상"을 결정합니다.

## 3. 인프라 설계 및 구현

### 3-1. CI/CD 파이프라인 (Jenkins)

```
Checkout → Build Frontend (npm ci + Vite build)
         → Build Backend (Gradle bootJar)
         → Deploy (docker-compose.prod.yml --build backend frontend ai)
         → Health Check (docker-compose ps)
```

- 민감 정보(DB 계정, JWT 시크릿, LiveKit API 키, OAuth 클라이언트 등 20여 개 Credential)를 Jenkins Credentials Store로 관리하고, 빌드 시 `.env` 파일에 주입하여 Git에는 절대 노출되지 않도록 설계했습니다.
- 배포 시 기존 `backend / frontend / ai` 컨테이너만 선택적으로 재빌드·재시작하여 `mysql · redis · livekit` 등 인프라 컨테이너는 무중단으로 유지했습니다.
- 빌드 완료 후 `docker image prune -f`로 불필요한 이미지를 자동 정리해 디스크 낭비를 방지했습니다.

### 3-2. Docker Compose 서비스 구성

```
mysql:8.0          — RDB (init.sql로 스키마 자동 초기화)
redis:alpine        — 게임 상태 저장소 / 세션 / 분산 락
livekit/livekit-server — WebRTC 미디어 서버
ai (FastAPI)        — AI 판결 서버
backend (Spring Boot) — REST API + WebSocket 게임 엔진
frontend (Nginx)    — React SPA 서빙
dozzle              — 전체 컨테이너 실시간 로그 모니터링
```

- 운영 환경에서 `backend · frontend · ai`는 `shared-network`로 묶어 컨테이너 간 통신하고, 외부 포트는 Nginx만 노출하도록 `expose` 전략을 사용했습니다.

### 3-3. Nginx 리버스 프록시

웹 서비스 특성상 **일반 HTTP API, WebSocket 업그레이드, LiveKit WSS, 내부 툴(Jenkins·Dozzle)** 4가지 프로토콜을 하나의 Nginx 인스턴스에서 처리해야 했습니다.

**핵심 설계 포인트:**

1. **HTTP → HTTPS 전체 리다이렉트** — Let's Encrypt 인증서 적용
2. **WebSocket (STOMP/SockJS) 업그레이드**
   ```nginx
   location /ws-stomp {
       proxy_http_version 1.1;
       proxy_set_header Upgrade $http_upgrade;
       proxy_set_header Connection $connection_upgrade;
       ...
   }
   ```
3. **LiveKit WSS 전용 서버 블록** — 포트 8880, `proxy_read_timeout 86400s`로 장시간 미디어 스트리밍 지원
4. **Docker 내부 DNS 레이지 로딩** — `set $upstream http://backend:8080;` 패턴으로 컨테이너 미기동 시에도 Nginx가 크래시되지 않도록 방어 처리

## 4. WebRTC — LiveKit 음성 통화 연동

### 4-1. 아키텍처 결정

초기에는 직접 WebRTC SFU를 구현하는 방안을 검토했으나, 게임 페이즈별 동적 권한 제어와 서버 사이드 권한 강제 적용이 필요하다는 판단 하에 **LiveKit SFU 서버**를 채택했습니다. LiveKit의 `RoomServiceClient` API가 서버에서 각 참가자의 publish/subscribe 권한을 실시간으로 변경할 수 있어 게임 로직과의 결합이 자연스러웠습니다.

### 4-2. JWT 토큰 기반 접근 제어

```java
// LiveKitService.java
public String createToken(String roomId, String userId, String name, String role) {
    AccessToken token = new AccessToken(apiKey, apiSecret);
    token.setName(userId);
    token.setIdentity(name);
    token.addGrants(new RoomJoin(true), new RoomName(roomId));
    if (role != null) {
        token.setMetadata("{\"role\":\"" + role + "\"}");  // 게임 직업 메타데이터
    }
    token.setTtl(3600);
    return token.toJwt();
}
```

- 방 입장 시 백엔드에서 서명된 JWT를 발급하여 프론트엔드에 전달하고, 클라이언트는 이 토큰으로만 LiveKit 룸에 접속할 수 있습니다.
- 토큰 메타데이터에 게임 직업(ALIEN/HUMAN 등)을 포함시켜 프론트엔드에서 역할 기반 UI를 렌더링할 때 활용했습니다.

### 4-3. 게임 페이즈별 마이크 권한 동적 제어

마피아 게임의 핵심 규칙인 **"밤에는 외계인끼리만 음성 통화 가능"** 을 서버 사이드에서 강제 적용했습니다. 클라이언트 측 처리만으로는 치팅 가능성이 있어 LiveKit RoomServiceClient로 서버에서 직접 제어했습니다.

```java
// GamePhaseService.java - applyLiveKitPermissionsForPhase()
for (RoomPlayer p : players.values()) {
    boolean canPublish;
    boolean canSubscribe;

    if (!p.isAlive()) {
        canPublish = false;   // 사망자: 발화 불가
        canSubscribe = true;  // 사망자: 관전(청취) 가능
    } else {
        canPublish = true;    // 생존자: 항상 발화 가능
        boolean isAlien = RoleStatus.ALIEN.name().equals(p.getRole());
        if (RoomPhases.DAY.equals(phase)) {
            canSubscribe = true;       // 낮: 모든 플레이어 청취 가능
        } else {
            canSubscribe = isAlien;    // 밤: 외계인만 청취 가능
        }
    }
    liveKitService.blockParticipantPubSub(roomId, p.getNickname(), canPublish, canSubscribe);
}
```

| 페이즈 | 생존 인간 | 생존 외계인 | 사망자 |
|---|---|---|---|
| DAY / DEFENSE / JUDGMENT | 발화 O · 청취 O | 발화 O · 청취 O | 발화 X · 청취 O |
| NIGHT / ALIENKILL | 발화 O · 청취 X | 발화 O · 청취 O (팀 통신) | 발화 X · 청취 O |

## 5. WebSocket 게임 엔진 설계

### 5-1. STOMP 엔드포인트 및 메시지 브로커

```java
// WebSocketConfig.java
registry.addEndpoint("/ws-stomp").setAllowedOriginPatterns("*").withSockJS();
registry.enableSimpleBroker("/topic", "/queue");
registry.setApplicationDestinationPrefixes("/app");
registry.setUserDestinationPrefix("/user");
```

- `/topic/room/{roomId}` : 방 전체 브로드캐스트 (페이즈 변경, 채팅, 플레이어 사망 등)
- `/topic/room/{roomId}/{userId}` : 개인 비공개 메시지 (역할 배정, 개인 액션 결과)
- `/app/**` : 클라이언트 → 서버 액션 (게임 시작, 특수 능력 사용, 변론 제출 등)

### 5-2. JWT 인증 인터셉터 (StompChannelInterceptor)

WebSocket 연결은 기존 Spring Security 필터 체인이 적용되지 않아 별도의 STOMP 레벨 인터셉터를 구현했습니다.

```
CONNECT 프레임 수신
  → Authorization 헤더에서 Bearer 토큰 추출
  → Redis 블랙리스트 확인 (로그아웃된 토큰 차단)
  → JwtProvider.validateToken() 검증
  → DB에서 사용자 조회 → userId(PK) 획득
  → StompPrincipal 설정 + 세션 속성 저장
SUBSCRIBE / SEND 프레임 수신
  → Principal이 없으면 세션 속성에서 복원 (SockJS 멀티 HTTP 요청 대응)
```

### 5-3. 게임 페이즈 스케줄러 엔진

```
DAY (60s) → DEFENSE (30s) → JUDGMENT (20s) → NIGHT (30s) → ALIENKILL (6s) → DAY …
```

**설계 도전 과제와 해결:**

1. **폴링 기반 페이즈 전환**
   ```java
   @Scheduled(fixedRate = 1000)
   public void checkAndUpdatePhases() {
       phaseStates.forEach((roomId, state) -> {
           if (isPhaseEnded(state)) {
               handlePhaseEnd(roomId, state);
               changePhase(roomId);
           }
       });
   }
   ```
   1초마다 각 방의 타이머 만료 여부를 확인하고 페이즈를 전환합니다. 상태는 `ConcurrentHashMap`으로 인메모리에서 빠르게 접근하고 Redis에도 동기화하여 서버 재시작 시 복원 가능하게 했습니다.

2. **DEFENSE 페이즈 내부/표시 시간 분리 (버퍼 트릭)**
   - 클라이언트에 표시되는 타이머: 30초
   - 서버 내부 타이머: 35초 (+5초 버퍼)
   - 이유: 클라이언트가 30초 타이머 종료 시 자동으로 변론을 제출하는데, 네트워크 지연을 고려해 서버는 35초까지 대기한 뒤 AI 판결을 트리거합니다.

3. **밀항자(PIRATE) 발포 이벤트 대응 — 페이즈 즉시 스킵**
   - 밀항자가 낮 시간에 총을 발사하면 해당 페이즈의 나머지 시간을 건너뛰고 6초 후 밤으로 전환해야 합니다.
   - `TaskScheduler.schedule()`로 딜레이 태스크를 예약하고, `ScheduledFuture<?>` 참조를 `ConcurrentHashMap`에 저장해 게임 종료 시 좀비 태스크가 남지 않도록 취소 처리했습니다.

### 5-4. 플레이어 사망 통합 처리

사망 이벤트는 여러 경로(AI 판결, 밀항자 총격, 외계인 야간 공격)에서 발생할 수 있어 `RoomBroadcastService.handlePlayerDeath()`로 일원화했습니다.

```
1. Redis에서 플레이어 상태를 isAlive=false로 갱신
2. LiveKit: blockParticipantPubSub(canPublish=false, canSubscribe=true)
3. STOMP /topic/room/{roomId}: 전체 방에 PLAYER_DEATH 브로드캐스트
4. STOMP /topic/room/{roomId}/{deadUserId}: 사망자에게만 전체 역할 공개 (ALL_ROLES)
```

## 6. Redis 활용 전략

| 용도 | 키 패턴 | 자료구조 |
|---|---|---|
| 방 정보 (RoomInfo) | `room:{roomId}:info` | String (JSON) |
| 플레이어 목록 (RoomPlayer) | `room:{roomId}:players` | Hash |
| 액션 기록 (RoomAction) | `room:{roomId}:turn:{n}:actions` | Hash |
| 변론 제출 (plea) | `room:{roomId}:day:{n}:pleas` | Hash |
| 판결 분산 락 | `room:{roomId}:day:{n}:lock` | String (NX EX) |
| 판결 결과 | `room:{roomId}:day:{n}:result` | String (JSON) |
| JWT 블랙리스트 | `blacklist:{token}` | String |

- 게임 상태를 Redis에 저장함으로써 서버가 재시작되어도 진행 중인 게임 상태를 복원할 수 있는 구조를 마련했습니다.
- 판결 로직에서 Redis `SET NX`(Not eXists) 패턴으로 분산 락을 구현해 단일 인스턴스 환경에서도 타이머 경쟁 조건(Race Condition)을 원천 차단했습니다.

## 7. 문제 해결 경험

### [문제 1] SockJS 멀티 HTTP 요청 시 Principal 유실

SockJS는 WebSocket 폴백 시 여러 HTTP 요청으로 세션을 관리합니다. STOMP `CONNECT` 이후의 `SUBSCRIBE` 프레임이 새 HTTP 연결에서 오면 `accessor.getUser()`가 `null`이 되는 현상이 발생했습니다.

**해결:** `CONNECT` 처리 시 `accessor.getSessionAttributes().put("userId", loginId)`로 세션 속성에도 userId를 저장하고, `SUBSCRIBE`/`SEND` 처리 시 `getUser()`가 null이면 세션 속성에서 복원하도록 방어 코드를 추가했습니다.

### [문제 2] Nginx에서 컨테이너 미기동 시 500 에러

`proxy_pass http://backend:8080`처럼 직접 지정하면 백엔드 컨테이너가 아직 시작되지 않은 경우 Nginx 자체가 시작되지 않거나 worker가 죽는 문제가 있었습니다.

**해결:** `resolver 127.0.0.11 valid=30s`(Docker 내부 DNS)와 `set $upstream http://backend:8080` 변수 패턴을 조합하여, 업스트림 컨테이너가 없어도 Nginx가 정상 동작하고 런타임에 DNS를 재조회하도록 설정했습니다.

### [문제 3] LiveKit 음성이 밤 페이즈에서 차단되지 않는 현상

클라이언트에서 `mute()` 처리만 했을 때 외계인 플레이어는 채팅창을 통해 팀원을 식별하기 어려워 서버 사이드 강제가 필요했습니다.

**해결:** `LiveKitService.blockParticipantPubSub()`으로 페이즈 전환 시마다 서버에서 각 플레이어의 `canPublish`/`canSubscribe` 권한을 LiveKit RoomServiceClient API로 직접 갱신했습니다. 이로써 클라이언트 치팅 없이 역할·생존 여부·페이즈에 따른 음성 격리를 서버에서 보장합니다.

## 8. 성과 및 배운 점

- WebSocket + WebRTC + REST API 세 가지 통신 채널을 하나의 Spring Boot 애플리케이션에서 통합 관리하는 아키텍처를 설계했습니다.
- Redis를 단순 캐시가 아닌 **게임 상태 저장소 + 분산 락** 용도로 활용하며 데이터 일관성을 유지하는 방법을 습득했습니다.
- LiveKit SDK의 서버사이드 제어 API를 통해 WebRTC 참가자 권한을 동적으로 조작함으로써 게임 규칙을 인프라 레벨에서 강제 적용했습니다.
- Jenkins + Docker Compose 기반 CI/CD 파이프라인을 직접 설계하며 인프라 자동화 전 과정을 경험했습니다.
- 타이머 경쟁 조건, SockJS 세션 분리, Nginx DNS 레이지 로딩 등 실제 운영에서 발생하는 엣지 케이스를 디버깅하고 해결하는 경험을 쌓았습니다.

> WebSocket(STOMP/SockJS) 기반 게임 엔진에서는 JWT 인증 인터셉터, 1초 폴링 페이즈 스케줄러, AI 판결 분산 락, 밀항자 이벤트에 따른 페이즈 즉시 스킵 등 실시간 멀티플레이어 게임에 필요한 핵심 기능을 Spring Boot에서 직접 구현했습니다.

> 이 경험을 통해 단순한 기능 구현을 넘어, 경쟁 조건 방지·치팅 방지·네트워크 지연 대응 등 운영 환경에서의 엣지 케이스를 고려한 시스템 설계 역량을 키울 수 있었습니다.
